1. Worum es geht – Grundbegriffe

Eine Software, die sich selbst aktualisiert, muss erkennen können, ob ein Update echt ist. Dafür signierst du jede Version: Das Werkzeug bildet über alle Dateien einer Version eine Prüfsumme und unterschreibt diese Liste mit deinem privaten Schlüssel. Die installierte Software kennt nur deinen öffentlichen Schlüssel und kann damit nachrechnen, ob jede Datei genau so ist, wie du sie signiert hast.

BegriffBedeutung
Privater SchlüsselBleibt auf deinem Rechner, mit Kennwort verschlüsselt (Ed25519). Wer ihn hat, kann in deinem Namen signieren – deshalb nie weitergeben, nur sichern.
Öffentlicher Schlüssel44 Zeichen Base64, z. B. Fy29YaD6…qVsc=. Steht in der Software, die prüft. Darf jeder sehen.
FingerabdruckKurzform des öffentlichen Schlüssels in Vierergruppen. Zum Vergleichen über einen zweiten Weg (Telefon, persönlich).
SIGNATUR.jsonListe aller Dateien mit Prüfsumme, Version und Signatur. Liegt im Wurzelordner der Version.
SIGNATUR-BAU.jsonNur Speedrace-Dashboard: Signatur der Bau-Dateien (Dockerfile, docker-compose.yml, tools/ …), aus denen das Docker-Image entsteht.
Tag v<Version>Markiert auf GitHub genau den signierten Stand, z. B. v1.8.12. Das Werkzeug setzt ihn selbst und verschiebt ihn nie.
ProfilEine Software mit ihrem eigenen Schlüssel, Repository und ihren Regeln, welche Dateien signiert werden.

2. Start, Oberfläche, Updates

Start: Signier-Werkzeug.exe doppelklicken. Das Werkzeug öffnet sich im Browser (nur auf diesem Rechner, unter 127.0.0.1, mit einem Zufallsschlüssel in der Adresse). Beim ersten Start warnt Windows evtl. „Der Computer wurde durch Windows geschützt“ – „Weitere Informationen“ → „Trotzdem ausführen“.

  • Reiter: Signieren · Prüfen · Profile & Schlüssel · GitHub · QNAP.
  • Nur eine Instanz: Ein zweiter Start öffnet die laufende Seite, statt ein zweites Werkzeug zu starten.
  • Beenden: mit „Beenden“. Läuft gerade etwas (Signieren, Hochladen, ein offenes Auswahlfenster), wird das abgelehnt, damit nichts halb erledigt bleibt. Ohne geöffnete Seite beendet sich das Werkzeug nach 10 Minuten von selbst – nie mitten in einem Vorgang.
  • Updates: Gibt es eine neuere Version, erscheint oben „Update“. Ein Klick lädt sie, prüft die Signatur des Herausgebers und startet neu. Ohne gültige Signatur ändert sich nichts.
  • Zwei Tabs: Hast du dasselbe Profil in zwei Tabs offen, lehnt das Werkzeug das Speichern aus dem älteren Tab ab („inzwischen geändert – neu laden“) – nichts wird still überschrieben.

3. Profile und Schlüssel

Im Reiter Profile & Schlüssel legst du je Software ein Profil an: „+ Profil „Speedrace-Dashboard““ für das Dashboard (feste Regeln) oder „+ Profil für andere Software“.

Profil anlegen

  1. Name, Regel („Welche Dateien werden signiert?“), GitHub-Repository (Besitzer/Name) und Zweig eintragen.
  2. Bei „andere Software“: Ausnahmen, je Zeile ein Muster – z. B. logs/* (ganzer Ordner) oder *.log. Ausnahmen gehören zum „Vertrag“ mit der Software: Änderst du sie, muss die Software sie gleich ändern.
  3. „Speichern“.

Schlüssel erzeugen oder übernehmen

  • Neuen Schlüssel erzeugen: Kennwort (mind. 12 Zeichen) zweimal eingeben. Das Kennwort wird nirgends gespeichert – gut aufbewahren.
  • Vorhandenen Schlüssel übernehmen: .pem-Datei wählen und ihr Kennwort eingeben.
  • Danach zeigt das Profil den öffentlichen Schlüssel mit „Kopieren“ – diesen trägst du dort ein, wo geprüft wird (beim Dashboard z. B. SR_UPDATE_SCHLUESSEL).
Sichern! Kopiere den Ordner schluessel im Datenordner (Reiter „Profile & Schlüssel“ → „Sicherung“ → „Ordner öffnen“) auf einen USB-Stick. Ohne Schlüssel kannst du keine neuen Versionen mehr signieren, die die installierte Software annimmt.
Schlüsseldatei fehlt? Ist für ein Profil schon ein öffentlicher Schlüssel hinterlegt, die Datei aber weg (z. B. auf den USB-Stick verschoben), zeigt das Werkzeug „Schlüsseldatei fehlt“ und lässt nur die passende gesicherte Datei wieder zu. Ein neuer Schlüssel würde die Prüfung in der Software brechen – dafür ein neues Profil anlegen.

Profil löschen: Die Schlüsseldatei wird nicht gelöscht, sondern umbenannt (….geloescht-Datum).

4. GitHub-Zugang

Zum Laden und Hochladen braucht das Werkzeug ein Fine-grained Token:

  1. GitHub → Settings → Developer settings → Fine-grained tokens → „Generate new token“.
  2. Repository access: nur die betroffenen Repositories.
  3. Permissions: Contents: Read and write; für „Neue Paketliste erstellen lassen“ beim Dashboard zusätzlich Actions: Read and write.
  4. Token im Reiter GitHub einfügen → „Speichern“.

Unter Windows wird das Token mit DPAPI verschlüsselt (nur für deinen Windows-Benutzer lesbar). In Meldungen und Protokollen wird es geschwärzt.

5. Eine Version signieren

Von GitHub laden, signieren und hochladen (empfohlen)

  1. In der Software VERSION erhöhen (genau x.y.z, ohne BOM), committen und pushen.
  2. Reiter Signieren: Profil wählen → „Von GitHub laden, signieren und hochladen“ → Kennwort.
  3. Das Werkzeug lädt den Stand des Zweigs, prüft ihn, signiert, lädt SIGNATUR.json (beim Dashboard auch SIGNATUR-BAU.json) in einem Commit genau auf diesen Stand hoch und setzt den Tag v<Version>.
  4. Erst jetzt die Version verteilen bzw. das Update einspielen.
Sicherheitsregeln beim Hochladen: Hat jemand zwischendurch etwas auf den Zweig gepusht, bricht das Werkzeug ab. Gibt es den Tag schon, bricht es ab, bevor etwas hochgeladen wird – ein Tag wird nie verschoben. Erneutes Signieren derselben Version lädt nichts doppelt hoch, sondern setzt nur einen fehlenden Tag.

Einen Ordner auf diesem Rechner signieren

„… oder einen Ordner auf diesem Rechner signieren“ aufklappen, Ordner wählen, „Ordner signieren“. Signiert werden alle Dateien darin – auch nicht eingecheckte (z. B. Thumbs.db). Für genau den Repository-Stand besser den GitHub-Weg nehmen. Liegt dort eine SIGNATUR.json mit fremdem Schlüssel, wird sie vorher im Datenordner gesichert.

Kompilierte Python-Dateien (__pycache__, *.pyc) werden nicht signiert, würden aber geladen. Liegen welche im Ordner, brechen Signieren und Prüfen ab – vorher löschen.

6. Paketliste signieren (Speedrace-Dashboard)

Neuere Python-Pakete – und, falls angegeben, cloudflared und ein getesteter Stand der Debian-Systempakete (OpenSSL, LibreOffice …) – sollen ohne neue Programmversion zu den Dashboards kommen – aber nur getestet und von dir signiert.

  1. Optional: „Neue Paketliste erstellen lassen“ startet die Action des Dashboards auf GitHub (sonst läuft sie wöchentlich von selbst). Das Werkzeug zeigt den Fortschritt (oft 10–30 Minuten). Danach: „Neue Paketliste liegt bereit“ – oder „keine neue Liste“ (keine neueren Pakete oder ein Test war rot; dann gibt es ein Issue im Repository). Das Token braucht dafür zusätzlich Actions: Read and write.
  2. Reiter Signieren, Speedrace-Profil wählen → „Paketliste prüfen“ (ohne Kennwort). Angezeigt werden Programmversion, Prüfsumme, cloudflared-Version, der Debian-Stand (z. B. „Debian trixie: Stand 24.10.2026 (bisher 26.09.2026)“) die geänderten Pakete gegenüber dem Tag (z. B. „pypdf 6.20.1 → 6.21.1“, auch „Prüfsummen geändert“ bei gleicher Version) und, getrennt davon, was sich gegenüber der zuletzt signierten Liste geändert hat (cloudflared, Wegfall einer Zeile). „bisher unbekannt“ heißt: die vorige Liste ließ sich nicht ermitteln – dann selbst nachsehen. Ändert sich nur cloudflared oder der Debian-Stand, ist die Liste trotzdem zu signieren.
  3. Änderungen ansehen. Passt alles: „Paketliste signieren und hochladen“ → Kennwort.
  4. SIGNATUR-PAKETE.json landet in einem Commit auf dem Zweig „pakete“. Nichts an main, kein Tag.
Das Werkzeug signiert nur, wenn die Liste zu einer gültig signierten Programmversion gehört (Tag v<Version> mit gültiger SIGNATUR.json), und genau die Liste, die du gesehen hast. Ist sie schon gültig signiert, meldet es „bereits signiert“. Enthält die Liste etwas anderes als Pakete mit Prüfsummen (z. B. --index-url, -r oder einen Direkt-Link), signiert es nicht – pip würde das übernehmen, ohne dass die Anzeige es zeigt.

7. Signatur prüfen

Reiter Prüfen: Profil wählen, dann „Stand auf GitHub prüfen“ (Zweig des Profils) oder einen Ordner wählen und „Ordner prüfen“. Das Werkzeug rechnet jede Datei nach.

Beim Speedrace-Dashboard werden zusätzlich die Bau-Dateien geprüft; eine angepasste docker-compose.yml ist bei einem Ordner nur ein Hinweis (sie wird vor Ort angepasst). Beim Stand auf GitHub heißt dieselbe Abweichung „nach dem Signieren geändert“.

8. QNAP: Dashboard auf dem NAS installieren

Der Reiter QNAP führt Schritt für Schritt durch die Arbeit auf dem NAS. Jeder Befehl wird vorher gezeigt und erst nach deiner Bestätigung in einem eigenen Konsolenfenster (Windows-ssh) ausgeführt. Dein Passwort tippst du nur dort – das Werkzeug sieht es nicht.

Vorbereitung

  • In QTS: Systemsteuerung → Netzwerk- & Dateidienste → Telnet/SSH → „SSH-Verbindung zulassen“; unter Windows 11 zusätzlich „SFTP aktivieren“.
  • QNAP-Profil ausfüllen: Host/IP, Port, Benutzer (Admin), Programmordner (absolut), optional Dashboard-Adresse, „Versionen von“ (dein Speedrace-Profil) → „Profil speichern“.

Abläufe

AblaufWofür
Neue Version installierenSignierte Version (Tag) laden und prüfen → hochladen → Container anhalten → alten Ordner beiseitelegen → entpacken → eigene docker-compose.yml vergleichen (und ggf. übernehmen) → Bau-Dateien prüfen → neu bauen → starten → kontrollieren → optional aufräumen.
Nur neu bauenGleiche Version, neues Image – z. B. für aktuelle Systempakete oder ein neues cloudflared.
Zur vorigen Version zurückDen beiseitegelegten Ordner zurückholen, prüfen, (falls nötig) neu bauen und starten.
AufräumenBeiseitegelegten Ordner endgültig löschen, hochgeladene ZIP und alte Images entfernen – erst, wenn die neue Version läuft. Am Ende zeigt es den Elternordner: übrige ….kaputt-…/….entpacken-…-Ordner von Hand löschen.

So arbeitest du einen Schritt ab

  1. Ablauf wählen → „Ablauf beginnen“. Freigegeben ist immer nur der nächste Schritt.
  2. Erklärung lesen. Der Befehl steht im grauen Feld („Kopieren“ für eigene Notizen).
  3. „Im SSH-Fenster ausführen“ → im Fenster ggf. Passwort eingeben → Ausgabe ansehen.
  4. Zurück im Werkzeug: „Hat geklappt“ oder „Fehler“ melden. Bei „Fehler“ helfen die „Typischen Fehler und Abhilfe“.

Eigene docker-compose.yml

Die neue Version bringt die signierte docker-compose.yml mit. Hast du deine auf der QNAP angepasst (Port, SR_UPDATE_SCHLUESSEL, SR_UID/SR_GID, .:/app:ro), wären diese Änderungen sonst weg. „docker-compose.yml vergleichen“ zeigt die Unterschiede (Zeilen mit „-“: signierte Fassung, „+“: deine). Weichen nur deine eigenen Anpassungen ab: „Eigene docker-compose.yml übernehmen“ – die Bau-Prüfung meldet danach bewusst Ergebnis 1. Bringt die neue Version selbst Änderungen an der Datei, überspringen und deine Anpassungen nachher von Hand eintragen.

Im Tag selbst ist jede Abweichung einer signierten Bau-Datei – auch der docker-compose.yml – ein Grund, nicht zu installieren: Dort gibt es nichts „vor Ort Angepasstes“.

Bau-Prüfung vor jedem Neubau

  • Steht statt „Ergebnis=…“ „Ergebnis fehlt“, lief keine Prüfung (z. B. sudo-Kennwort falsch, Container läuft nicht) – „Fehler“ melden.
  • Ergebnis 2 sperrt den Neubau für genau diese Dateien. Kommt ein anderer Stand in den Programmordner (neue Version, Rückweg), fällt die Sperre. „Bau-Sperre aufheben“ nur, wenn du die Bau-Dateien selbst aus der signierten Version neu geholt hast.
  • Hat die Installation noch kein neues Image gebaut (z. B. ohne Internet), darf der Rückweg den Neubau überspringen.
Nicht am Tag vor oder am Veranstaltungstag umbauen. Das Werkzeug fasst im Elternordner nur den Programmordner, die selbst angelegten ….alt-…/….kaputt-…/….entpacken-…-Ordner und die eigenen ZIPs an – den Daten-Ordner nie. Alles steht im Protokoll („Ordner mit Protokoll öffnen“).

9. Andere Software einbinden (Prompt zur Einbindung)

Für ein Profil „andere Software“ mit Schlüssel erzeugt „Prompt erzeugen“ einen Text für eine KI-Sitzung, die im Repository dieser Software die Prüfung einbaut: mit öffentlichem Schlüssel, Fingerabdruck, Ausnahmen, Regeln, Ablauf und dem Prüfmodul Pruefmodul/signatur_pruefen.py. Er enthält kein Token und keinen privaten Schlüssel.

  • Der Schlüssel ist in der Software nur Voreinstellung; ersetzen darf ihn nur der Betreiber (Umgebungsvariable/Admin-Einstellung), nie eine Datei aus einem Update.
  • Tags setzt nur das Signier-Werkzeug – keine automatischen Tag-Workflows in der Software.
  • Die Software prüft vor dem Installieren und installiert genau den geprüften Ordner.

10. Das Werkzeug selbst veröffentlichen (Herausgeber)

Nur für den Herausgeber des Signier-Werkzeugs (Reiter GitHub → „Signier-Werkzeug selbst“, Abbildung 6):

  1. VERSION in signier_werkzeug.py erhöhen und nach main bringen.
  2. „Bau starten (Tag setzen)“: setzt v<Version> auf main; GitHub baut die exe (feste Paketversionen, Tests, Selbsttest, Herkunftsnachweis) und legt einen Entwurf an. Fortschritt: „Bau-Status prüfen“.
  3. „Neuen Entwurf signieren und veröffentlichen“ → Kennwort: prüft die Herkunft der exe (Prüfsumme aus dem Bau, Tag auf dem gebauten Commit, Commit auf main), signiert sie und veröffentlicht das Release. Erst dann sehen andere Installationen das Update.

Was das Werkzeug für dich absichert

  • Die Oberfläche läuft nur auf diesem Rechner; jede Anfrage braucht den Zufallsschlüssel der Sitzung.
  • Das Token geht nur an GitHub und wird in Meldungen geschwärzt.
  • Archive von GitHub werden vor dem Entpacken geprüft (keine Pfade nach außen, keine Verknüpfungen, Größen- und Mengengrenzen).
  • Dateien werden atomar geschrieben – ein Abbruch hinterlässt keine halbe SIGNATUR.json.
  • Updates des Werkzeugs werden nur mit gültiger Signatur des Herausgebers eingespielt.
